## [Unreleased]
### Added — Phase 7 (fulfilment, couriers, returns) — in progress
- Phase 8, slice 2 — the right to download: Orders now announces **`OrderPaid`** (through the outbox, in the same transaction, once, when an order's payment first becomes paid); DigitalProducts listens and makes one **entitlement** per digital order line (`entitlements`: UNIQUE per order line, downloads used can never pass the limit — a database CHECK —, status only active → revoked by a trigger, expiry worked out from `expires_at`, never stored; granted with the product's own limit and days, else the shop default of 5 downloads and no expiry, setting `digital.download_limit`). Granted even if the file is not uploaded yet. Read through a new Orders contract `DigitalOrderLines` (paid orders only). **Cash on delivery is now refused in code for any cart with a digital or service line**, however the payment method is set up. The owner is never copied onto the entitlement: it is resolved through the order. Tests: 12 feature + 2 multi-process (six parallel grants make one right per line); four rules were each broken once to prove tests fail.
- Phase 8, slice 5 — versions, refunds and the refund policy: **Refund policies** are data (`refund_policies` + translations; rules *never refundable* / *until first use* / *for N days*; a switch for whether a fully refunded order loses its downloads and keys; one default, a product may choose its own; seeded default: refundable until first use; English required, Bangla falls back to it) edited by staff at Refund policies, and their words are shown on the product page of a digital product and on the checkout review, in the customer's language, from the records (read through the new `RefundPolicyTexts` contract). `entitlements.first_used_at` (set once by the first download or first look at the keys) feeds the *until first use* rule. Orders now announces **`OrderRefunded`** (full or partial, outbox, once); on a **full** refund DigitalProducts takes away the order's downloads and withdraws its keys (never returned to the pool) where the policy says so; a partial refund changes nothing automatically. **Customer downloads** (staff, by order number): what was used, what the policy says (advice only — the refund itself is decided in Payments), and extend time / add downloads / start the count again / take away with a reason — every change audited with before and after; a revoked right is never touched. Uploading version 2 or later announces **`DigitalAssetVersionPublished`**, and each owner with an email gets one message per version (a database UNIQUE; a failed send is taken back and retried; revoked rights are not told; guests get a signed link). Tests: 16 + 12 feature tests, 1 more multi-process test (a refund against eight parallel downloads); seven rules were each broken once to prove tests fail.
- Phase 8, slice 4 — licence keys: staff add keys to a product's pool from a text file, one per line (admin: Digital files → the product; up to 5,000 lines of 200 characters; blanks, a header and a byte-order mark ignored; repeats and bad lines counted and skipped; the file is never stored); keys are **encrypted** with the app key and fingerprinted (HMAC) so a repeat is found without keeping the key; a database trigger freezes the key and lets only its state move (available → given → withdrawn, the owner set once). **One key per unit bought** is given when the order is paid (`entitlements.keys_needed`), lowest key first, with `FOR UPDATE SKIP LOCKED` and a guarded update; if the pool is short the customer keeps their right, sees "being prepared", and is filled automatically, oldest order first, when more keys are imported (and by a 15-minute check that also logs an ERROR `digital.alert keys_short` once an hour per product). Customers see how many keys are ready in My downloads (never the keys) and a "Show my keys" POST opens them on a `no-store` page — for signed-in owners and for guests in their code session; someone else's keys are "not found" and logged; keys stay visible after downloads run out or time passes, never after a right is revoked; each showing is audited as a count and key ids only. A product with keys and no file has no download button. Tests: 21 feature + 2 multi-process (twenty customers racing for twelve keys; three overlapping imports racing with allocations); five rules were each broken once to prove tests fail.
- Phase 8, slice 3 — downloads: **My downloads** (`/account/library`, signed-in customers: their own orders' downloads with file, version, downloads left and expiry; read in a fixed number of queries; no storage path or address is ever in a page) and **guest access** (a signed expiring link, a code by SMS to the order's phone — purpose `guest_access`, the existing rate-limited code service — then 30 minutes of access to that one order). **`DownloadDigitalFile`** is the one place a download happens: the newest file must exist (no download is charged for a missing file), then ONE conditional UPDATE adds one only while the right is active, not expired and under its limit, then a signed storage address valid for about 60 seconds is made (saved under the original name, Bangla included) and the attempt written to the append-only **`download_logs`** (counter, address and log are one transaction: nothing is used if any part fails). Refusals (revoked, expired, limit reached, no file) say why, are logged and use nothing; someone else's download is "not found" and logged as `not_owner`. The download is a POST so a link preview cannot use one up; the answer is a 303 to the signed address with `Cache-Control: no-store`; the address is never stored or logged. New read-only Orders contracts `CustomerOrders` and `OrderDirectory::findByPublicId`; the phone-code contract takes a purpose. Links appear on the account order page and the confirmation page for a paid order with downloads. Tests: 18 feature + 1 multi-process (10 parallel downloads at a limit of 3 grant exactly 3) + 1 against the real local bucket (SeaweedFS: bucket refuses anonymous access, our signed address works, saved under its real name); five rules were each broken once to prove tests fail.

- Slice 7 — courier statements (Shipping; contract in Payments): `ImportCourierStatement` checks a courier's statement against our own records and records the cash it paid over. A plain CSV `consignment_id,status,cod_amount,courier_fee,delivered_at` for one courier and a period of at most 31 days (a provider-neutral format: no saved courier document describes one); a malformed file is refused as a whole with the line numbers; the same file or the same statement number is checked once. A parcel we do not know, a status that disagrees with ours (where the courier can be asked, it is asked first and our own state follows its answer; the statement itself never changes a parcel), a different cash amount, a delivered cash parcel of this courier in the period that the statement leaves out, a parcel already covered by an earlier statement, and money paid when nothing is waiting for it each become an item in the new parcel exception queue (`shipment_exceptions`, new types `statement_*`). The cash of the delivered parcels is recorded as the courier's payment through the new `Payments\Contracts\CodCashLedger`: **what arrived plus what the courier kept (its delivery and return charges, new `cod_remittances.fee_minor`) must equal the cash we collected**, otherwise a short or surplus payment becomes a reconciliation exception. Tables `courier_statements` and `courier_statement_lines` (never changed or deleted; what the courier charged for each parcel is kept for reporting). `ResolveShipmentIssue` closes a queue item as resolved or ignored with a note, first to close wins. Tests: 16 feature tests and 2 multi-process tests (the same statement imported by five at once → one record, one cash entry, each problem once; three different statements claiming one parcel at once → the parcel's cash on one statement only); the fee arithmetic, the missing-parcel check, the already-covered check, asking the courier and the cash-amount check were each removed once to prove a test fails without them.
- Slice 6 — inventory operations (Inventory): **transfers between places** (`CreateStockTransfer`: the units leave the source at once, one ledger row each, only units not promised to an order, all lines or none; `ReceiveStockTransfer`: staff say how many arrived, onto the shelf with a ledger row each, what did not arrive is recorded as lost on the line, once; `CancelStockTransfer`: only while on its way, every unit goes back; stock kept in quarantine can be moved back to the main place once fit to sell). **Stock-take** (`OpenStockCount` for a whole place or chosen products, one active count per place by a database UNIQUE; `RecordStockCount`; `SubmitStockCount`: every product counted, then what the books say now is set against the count and each difference is fixed as the correction for approval; a count with no differences needs nobody; `DecideStockCount`: a SECOND person approves (the database refuses the same person too, by trigger) and stock is corrected by each difference with a `count` ledger row, all or none, or refuses with a reason; a correction that would take stock below what is promised to orders changes nothing and says so). **Reports**: low stock per place (never counting quarantined stock) and stock aging (days since the last sale, or since arrival, in 0-30 / 31-60 / 61-90 / 91+ buckets, in units; the system has no cost price). Tables `stock_transfers` (+items; status moves by trigger, compared with the enum in a test; what arrived is set once), `stock_counts` (+lines). Purchase orders and suppliers stay a backlog epic as agreed. Tests: 20 feature tests and 4 multi-process tests (transfers racing an order's hold for the last free units → one winner; a transfer received by six at once → once; five opening a count → one; approvals and a refusal at once → one decision); the reserved-units guard, the second-person rule, the correction, the all-counted rule, the receive lock and the one-count-per-place unique were each removed once to prove a test fails without them (removing only the reserved-units guard is NOT caught by the race test because the stock table's own CHECK still refuses: defence in depth). Found while testing: MariaDB refuses a CHECK on a column whose foreign key sets it to NULL on delete (the two-person rule is therefore a trigger), and a generated marker column must be in the append-only list when it moves with the status.
- Slice 5 — returns (Shipping; contracts in Inventory and Orders): `RequestReturn` (a customer for their own order, within the return window counted from the day the parcel arrived — default 7 days, setting `shipping.return_window_days` — staff at any time; someone else's order, a guest or an unknown order are all "not found"; only delivered goods, never more than delivered less what is already back or already asked for, counted with the order row locked), `DecideReturn` (allow with who pays the postage recorded but never charged, refuse with a reason, withdraw; the first decision wins), `ReceiveReturn` (staff say how many of each line really came back; counted as returned on the order through one conditional UPDATE on `order_items.returned_qty` and the order moves to partly/fully returned; a return where nothing came back closes at once) and `InspectReturnItem` (restock: back on the shelf where it left from, for sale again; quarantine: kept in a new non-sellable `quarantine` location, never counted as available or reserved; write off: counted in and out again so the ledger shows it; decided once per line, ledger rows in the same transaction). When the last line is looked at the return closes with a **refund suggestion** (what was paid for the goods that came back, rounded down, delivery excluded; 0 for a cash order whose parcel never arrived): nothing is ever refunded from here. A parcel the courier brings back (`shipping.returned`) opens a return for everything in it, already allowed, once per parcel (generated-column UNIQUE), and receiving it resolves the parcel's `returned_to_origin` alert. Tables `return_requests` (status moves enforced by trigger and compared with `ReturnStatus` in a test; closed needs its times and suggestion) and `return_items` (what came back and what was decided are set once). Rule changes: the order's fulfilment state may go from partly fulfilled to partly/fully returned; stock locations have a `quarantine` type. Cleanup: Shipping now asks Orders for an order's public id through `OrderDirectory` instead of reading the orders table. Tests: 20 feature tests and 2 multi-process tests (six simultaneous requests for the last unit → one; five receives → one; six inspections of one line → one); the capacity guard, the ownership check, the window, the cash-origin rule and the quarantine exclusion were each removed once to prove a test fails without them. Found and fixed while testing: taking stock out through an insert-or-update tripped the on-hand CHECK, so write-off uses a conditional UPDATE.
- Slice 3 — courier events, delivery and cash (Shipping, Orders, Payments): `RecordCourierEvent` takes one thing a courier said (webhook or polling): stored once in the courier's own words and time (UNIQUE parcel + word + time), the parcel's state follows the LATEST event by the courier's time (never the arrival order, never back out of delivered/returned), a word with no meaning in `courier_status_map` is kept, raised once to the new `shipment_exceptions` queue and changes nothing else (the order is untouched), an unknown parcel is raised too. Leaving the shop, delivery, a failed attempt (attempts counted from the events; the 3rd, `SHIPPING_MAX_DELIVERY_ATTEMPTS`, raises `attempts_exhausted`) and a return are announced through the outbox. `POST /api/v1/webhooks/couriers/{courier}` (adapter authenticates; failing requests refused and stored nowhere; own rate limit) and `PollCourierShipments` every 10 minutes (least recently asked first via `shipments.polled_at`, one unreachable courier never stops the others). `RecordManualShipmentStatus`: staff record the journey by hand with the same rules and their name kept, so the manual courier works end to end (a time before the latest recorded event is refused). **Delivery records the parcel's cash once** (`RecordCodCollection::forShipment`, by the `ShipmentDelivered` announcement: once per parcel by four independent guards — the consumer, an exists check, UNIQUE shipment_id and the unique payment reference): a normal paid payment per parcel, so refunds work as for any money; the order is **partly paid** (new payment state `partially_paid`) until the parcels' cash reaches the order total, then paid; an order whose last parcel arrived gets `delivered_at` (set once, by trigger) and **completes** when delivered and paid, whichever announcement arrives last. The whole order total can no longer be recorded by hand once parcels exist (`cod_use_parcels`). The customer gets an SMS (English/Bangla) when the parcel leaves, is delivered, fails (and finally fails). Tests: 28 feature tests and 7 real multi-process tests in the shipping suite (the same delivery reported by 6 processes at once and announced by 4 workers plus a redelivery → one collection and one completion; out-of-order messages in concurrent processes → right final state); the arrival-order rule, the final-state rule, the all-delivered flag, the unknown-status queue and the four cash guards were each removed once to prove a test fails without them. Honest note: removing only some of the cash guards is NOT detected because the others still hold (defence in depth); only removing all four fails.
- Slice 2 — making a parcel (Shipping; contracts in Orders and Inventory): `CreateShipment` makes one parcel for an order, whole or in part, in ONE transaction with the order row locked first (so it cannot be cancelled or shipped by someone else at the same moment): quantities are counted as shipped through one conditional UPDATE on `order_items.fulfilled_qty` (never more than ordered), the stock leaves the warehouse for those quantities only (`ShipmentStock::commit`; a hold is split when only part ships; one ledger row per movement), the order's fulfilment state follows (unfulfilled → partly → fulfilled; the first parcel moves the order to processing) and the parcel, its lines and first history entry are written. Cash on delivery: the parcel that completes the order collects whatever is left of the total (delivery charge, fee and rounding included), an earlier parcel its lines' share, so the parcels always add up to the order total exactly; a prepaid order collects nothing. An order that is not confirmed, is cancelled, is under review, or is online and unpaid cannot be shipped; digital and service lines are never posted. `BookShipment` books with the courier as a separate, repeatable step (set once, so pressing it twice books once): when the courier cannot be reached the parcel and its stock stand and staff book again later. `HandOverShipment` (a parcel to be booked cannot leave unbooked) and `CancelShipment` (only before handover; tells the courier first and stops if it refuses; puts the stock back into the order's hold with a ledger row `shipment_cancelled`, takes the counts down and moves the order back; the order can be cancelled again afterwards). Rule change in Orders: the fulfilment state may step back (partly → unfulfilled, fulfilled → partly) when a parcel is cancelled before it leaves. Tests: 22 feature tests and 5 real multi-process tests (parcel vs cancel of its order, 5 ships of the last units → one, cancel vs handover, one booking, and a deterministic proof that the order row is the lock); the over-ship guard, stock commit, stock put-back and the order lock were each removed once to prove a test fails without them. Honest note: the random cancel-vs-ship race alone did NOT detect the missing order lock (the stock hold also serialises most interleavings), so the deterministic lock test was added.
- Slice 1 — shipment domain and the courier contract (Shipping; `StatusFlow` moved to Platform and shared, Payments keeps a thin alias): tables `courier_accounts` (credentials encrypted, never in arrays/JSON), `courier_status_map`, `shipments` (status moves enforced by a database trigger that a test compares with the `ShipmentStatus` enum; courier id set once; cash this parcel collects; delivered/handover times required by CHECK), `shipment_items`, `shipment_events` (append-only, one per parcel/status/time). `CourierProvider` contract (create, cancel, track, parse webhook, capabilities), `CourierRegistry`, and `ManualCourier` (staff enter tracking; talks to nobody, so it works when every courier API is down), seeded with the manual account. Over-shipping is guarded by the existing `order_items.fulfilled_qty` CHECK (used in slice 2 through an Orders contract). Tests: 16 (every status move checked against the enum); the move rules, the set-once id and the credential encryption were each broken once to prove a test fails without them.

- Slice 8 — admin screens for money (Payments; small additions to Orders and IdentityAccess), English and Bangla, all through the same Actions as everything else: **Money today** (online paid, cash collected, refunded today in the shop's Dhaka day; refunds waiting; payments needing review; open reconciliation items; cash-on-delivery aging); **Payments** list (search by order number, payment id, our reference or bank id; filter by state; no extra queries for longer lists) and **payment page** (attempts, refunds with who asked and who approved, reconciliation items, the gateway's raw notifications with secrets, card numbers, phone numbers and verification signatures hidden and the stored copy never changed, "ask the payment service again", refund request form); **Refunds** queue (approve, reject with reason, send, mark paid back by hand with proof); **Cash on delivery** (aging, record cash by order number, enter a courier statement from the list of collected cash); **Reconciliation** (open items with filters, close with a note, upload a settlement file, history of files checked); **Payment settings** (pause/resume online payments, refund second-approver limit, which methods are offered, provider health from our own records). Each upload/action has its own rate limit per person and per route (Laravel's `throttle:N,M` shares one counter per person across all routes, which let unrelated screens eat each other's allowance). New small contracts: `Orders\Contracts\OrderDirectory::findByNumber`, `IdentityAccess\Contracts\StaffDirectory` (names only). `Redactor` now also hides `verify_sign` / `verify_key`. Tests: 28 feature tests (permission matrix for every route, both languages, every flow through HTTP, redaction, query count, escaping, rate limit); permission checks, redaction and the pause switch were each removed once to prove a test fails without them.
- Slice 7 — reconciliation (Payments): (1) **scheduled check** every 10 minutes (`ReconcilePendingPayments`): online attempts still unfinished after 10 minutes (`payments.reconcile_after_minutes`) are put to the gateway, so a payment whose notification never arrived is still found; a payment still open 2 hours (`payments.long_pending_hours`) after its time limit is raised to finance as `long_pending`. (2) **Settlement file check** (`ImportSettlement`, table `settlement_imports`): a plain CSV `reference,bank_txn_id,amount,currency,settled_at` for one provider and a period of at most 31 days; a malformed file is refused as a whole with the line numbers; the same file is checked once (hash UNIQUE, also against two uploads at once). A line we do not know → `unmatched_provider_txn`; a different amount → `amount_mismatch`; currency → `currency_mismatch`; a different bank id → `unmatched_provider_txn`; our paid attempts verified inside the period that the file omits → `orphan_payment`. **A file never makes anything paid**: a line that says paid while we show unpaid is put to the gateway and only its answer counts. This is NOT a provider-specific format: no saved provider document describes a settlement file yet; mapping a real SSLCommerz report needs its documentation saved first. (3) **Closing exceptions** (`ResolveReconciliationException`): resolved or ignored, a note required, the first person to close wins, audited, moves no money. Each problem is raised once (UNIQUE type + reference). Tests: 25 feature tests and 2 real multi-process tests (5 simultaneous uploads of one file → one check, 3 exceptions; 6 people closing one exception → one); each safeguard was removed once to prove a test fails without it. Permission `payments.reconcile` and the screens arrive in slice 8.
- Slice 6 — cash on delivery: collection, courier statements, aging (Payments; small `CodOrders` contract in Orders): staff record that the cash for a COD order was collected (the amount is always the order's total, so it cannot be mistyped; once per order, enforced by a database UNIQUE so two people recording the same delivery at once cannot both succeed; date cannot be in the future or before the order). The cash becomes a normal paid `payments` row (provider `cod`) with one succeeded attempt, so refunds work exactly as for online money (always by hand with proof), and the order follows through the outbox (payment status `paid`; the order's progress is not moved). Courier statements: staff enter a statement (courier, statement number, amount received, the parcels it lists with what the courier says it paid for each); the expected total is what OUR collections add up to; the statement is `reconciled`, `short` or `over` (a `cod_short` / `cod_over` exception for finance), or `pending` when the total agrees but a parcel does not (`amount_mismatch` exception). A statement can be entered once per courier and a parcel can sit on one statement only (database UNIQUEs). Aging report (`CodAging`): cash not yet collected (confirmed/processing/completed COD orders) and cash collected but not yet remitted, in 0-3 / 4-7 / 8-14 / 15+ day buckets. Migrations add `cod_collections.payment_id` and a unique marker so an order has one hand-recorded collection (each shipment, later, collects its own). Tests: 23 feature tests and 5 real multi-process tests (8 simultaneous recordings of one delivery → one; 6 statements claiming one parcel → one; 5 entries of one statement → one); each database guard was removed once to prove a test fails without it. Permission `payments.cod` is enforced at the routes in slice 8.
- Slice 5 — refunds (Payments, small change in Orders): staff **request** a refund (amount, reason, optionally for one specific attempt), a person **approves** it (a different person above ৳5,000, editable setting `payments.refund_second_approver_minor`) or **rejects** it (reason required), then it is **sent** to the gateway or, when the gateway cannot do it, **completed by hand with proof** (bank/bKash reference). Money given back can never pass money received: the amount is reserved on the payment with one conditional `UPDATE … WHERE refunded_minor + ? <= captured_minor` under the payment row lock (database CHECK as backstop), and a rejection or gateway refusal gives it back. A refund sent to the gateway carries our own unique `refund_ref`; "accepted/processing" stays `processing` until the gateway says refunded (scheduled `PollRefunds` every 5 minutes; unreachable gateway → same call repeated after 60 seconds; stuck over 3 days → `refund_stuck` exception). A second paid attempt on one payment (duplicate payment) can be refunded within that attempt's own amount. `payments.refund_succeeded` reaches the order through the outbox: full → `refunded`, partial → `partially_refunded`, extra/late → note only; Bangla/English SMS; a fully refunded order can now be cancelled. Migration adds `refunds.payment_transaction_id`. Tests: 38 feature tests and 7 real multi-process tests (12 simultaneous 10% requests → exactly 10 accepted; 6 × 60% → exactly 1; four simultaneous approvals → one; six simultaneous sends → the gateway asked once); each safeguard was removed once to prove a test fails without it.
- Slice 4 — the hostile-callback suite (tests and a probe command; no behaviour change except that nothing was found wrong): a 24-story **replay suite** (duplicates, the same payment through every channel at once, browser-before-notification and the reverse, failure-then-success in one session, cancel-then-success, late "failed" notices after payment, success after the time limit, after staff cancelled the order and four days after a failure, forged notifications, amounts too small / too large / one paisa out, another currency, another transaction's answer, no bank transaction id, a notification for a transaction that is not ours, gateway down then back, two attempts both paid) in which the same money rules are checked after EVERY step: never more captured than asked, no money without a verified attempt that has its bank id, paid exactly when the order is paid, at most one "paid" announcement per payment, a paid order is never also told it expired. **Real multi-process tests** (eight OS processes, own database connections, released together): eight simultaneous verifications → one payment taken and one announcement; two attempts both reported paid → money taken once, the extra flagged for refund; one notification delivered eight times at once → stored once, paid once; "failed" reports racing "paid" ones → always paid, never undone; success racing the expiry job → either paid, or expired AND recorded as a late payment (never lost, never invented); a committed-but-never-dispatched announcement (a crash) → delivered once by four racing workers and again harmlessly on redelivery. Each safeguard was removed in turn (row lock, notification de-duplication, amount and currency checks, "can this order still take the money") and the tests failed every time.
- Slice 3 — the SSLCommerz adapter (sandbox first), written only from the saved official documentation: starts a session (`POST /gwprocess/v4/api.php`) and sends the customer to the returned `GatewayPageURL` **only if it is an https address on sslcommerz.com** (a tampered answer cannot redirect a customer elsewhere); asks about a payment by validation id (Order Validation API) or by our own reference (Transaction Query API); requests refunds and reads refund status. A validation id that turns out to belong to another transaction is dropped and our own reference is asked instead (so borrowing someone else's paid id neither pays nor falsely alarms). Amounts are read exactly in paisa; when the two BDT amount fields disagree, or the text is not an exact amount, no amount is returned and the payment is held for a person. A high-risk rating still pays but holds the order for review instead of confirming it. `verify_sign` is not used (its recipe is not documented). Partial refunds are not declared (not shown in the documentation). The store password sits in the query string of the GET calls by SSLCommerz's own design, so an HTTP error is never logged or passed on as is: only the kind of failure is, and a test checks that the password and store id appear in no table row, outbox message, note or log line. **Fixed a flaw found while reading the docs:** SSLCommerz can report a failed try and then a success under the same transaction id (the query API returns several results per id), but an attempt closed as failed could never become paid, so a real payment would have been lost. A failed, cancelled or expired attempt may now still be found paid (the database allows exactly that one move; a paid attempt never changes), for a week after it started; more than one successful payment under one reference raises a "duplicate payment" for finance. The gateway is available only when credentials are set; the live bank needs production, sandbox off and `PAYMENTS_ALLOW_LIVE=true` all together, so a development machine holding live credentials cannot reach it. Tests now blank provider credentials and fail on any real HTTP request. Opt-in sandbox checks (not in CI) are in `app/Modules/Payments/tests/Sandbox/`.
- Slice 2 — paying an order online (Payments, Orders): "Pay online" appears at checkout only when the owner has switched it on, a gateway is set up, the payments freeze is off, and the order is inside the method's amount limits; downloads and services can now be bought. The order is placed unpaid with its stock held, then the customer is sent to the gateway. **A payment becomes "paid" in exactly one place (`VerifyPayment`)**: it asks the gateway server to server about OUR reference and requires the same reference, amount and currency (and a bank transaction id, without which a refund would be impossible) under the payment's row lock; anything else is held for a person as "needs review" and never paid; repeating it, or two at once, changes nothing. The browser return page and the gateway notification only say WHICH transaction to ask about: a forged "success" page or a forged "VALID" notification leaves the order unpaid (tested). Notifications are stored exactly as received (same one twice = stored once), answered at once and processed from a queue with back-off; return links are signed, expiring and exempt from CSRF only because they are. Retry after a failure is a new numbered attempt on the same payment (`VM-2610-000123-2`); pressing "pay" twice within two minutes gives the same gateway page rather than a second session; the database allows one open payment per order. Orders follow their payment only through outbox events (paid → paid and confirmed unless flagged; failed; expired → cancelled with stock released; mismatch → flagged with a note), each applied once. Unpaid online payments expire after 30 minutes (asking the gateway one last time first, so a customer who paid is never expired); money that arrives after expiry or for a cancelled order is recorded as a late payment for staff, never lost and never silently accepted. Cash orders nobody confirms are auto-cancelled after 3 days (setting `orders.pending_cancel_days`, 0 = never), freeing stock and telling the customer in their language. Order page shows paid / due / cancelled / refunded states with "Pay now" and "Check again". Online orders are not subject to the cash-order limits. Not yet: the real SSLCommerz adapter (slice 3); refunds (slice 5); admin screens (slice 8).
- Slice 1 — payment domain and gateway contract (new `Payments` module): tables `payment_methods` (+ translations), `payments`, `payment_transactions`, `payment_webhook_events`, `refunds`, `cod_collections`, `cod_remittances` (+ items), `reconciliation_exceptions`. The database refuses: amounts of zero or less, more received than asked, more refunded than received, rewriting what was agreed (amount, order, provider), deleting any payment record, the same bank transaction or notification stored twice, and any status change the state machine does not allow (a paid payment going back to pending, a final attempt changing again); a test runs every pair of statuses through the real triggers and compares with the enums so they cannot drift apart. `PaymentGateway` contract (initiate, parseCallback, verify, status, refund, refundStatus, capabilities) with `GatewayRegistry`, and a `FakeGateway` that plays any provider answer for tests and never touches a network. Payment methods seeded once: cash on delivery (on) and "Pay online" via SSLCommerz (off until credentials are in). SSLCommerz's official documentation is saved in `docs/vendor/sslcommerz/` with what it does not say (the `verify_sign` recipe is unconfirmed, so authenticity rests on server-to-server validation).
